data-v2-service：当前需求与长期规划（2026-01-31）

==================== 0. 背景与动机 ====================
当前仓库已有 data-service，主要面向 Binance 行情采集与 TimescaleDB 落库，并围绕固定表结构（如 candles_1m、metrics_5m）运行。
现阶段新增诉求是：在不被既有表结构束缚的前提下，先以单币种试运行，验证“全字段收集”的可行性，并为后续多工具/多市场扩展打下统一骨架。


==================== 1. 当前明确需求（短期目标） ====================
1.1 新建服务（预览版）
- 服务位置：services-preview/data-v2-service
- 服务形态：Python 微服务（与仓库其它服务一致：pyproject.toml/requirements/Makefile/scripts/start.sh）
- 目录骨架：src/marketdata 下实现“行情采集引擎”

1.2 采集方式定义（核心约束）
- REST 与 WS 的含义：它们不是“对外提供的 HTTP API/WS API”，而是“行情数据获取方式/采集方法”：
  - REST/：通过 HTTP REST 拉取市场数据
  - WS/：通过 WebSocket 订阅市场数据

1.3 工具适配器命名规范（核心约束）
- 适配器文件用“工具名称”命名，例：
  - src/marketdata/REST/CCXT.py
  - src/marketdata/WS/CCXT.py
- 适配器目标：用该工具在对应采集方式下，尽可能获取“可获取的全部字段”

1.4 “全字段并集”（Union-of-fields）
- 需要一个统一的字段并集构造逻辑：
  - 采集器负责产出样本（raw）
  - union 层负责观测与合并字段空间（并集）
- 输出目标：
  - 可观察每类行情数据（ticker/trades/orderbook/ohlcv 等）的字段并集大小与字段样例
  - 为后续落库/回放/结构化映射提供依据

1.5 运行策略（先小后大）
- 先只跑一个币种（单 symbol），减少不确定性与成本
- 代理要求：采集需支持走本地代理（如 127.0.0.1:7890）


==================== 2. 数据库与存储规划（中期目标） ====================
2.1 新建数据库（端口 5344）
- 目的：将“全字段收集/实验性数据链路”与既有生产链路隔离，避免污染与 schema 扩张风险

2.2 存储分层原则
- raw 为唯一真相源（Single Source of Truth）：
  - 所有采集到的原始事件先落 raw（建议 JSONB）
  - 结构化表仅为读优化，可由 raw 回放重建
- 引入检查层（quality）：
  - 连通性、延迟、吞吐、缺口、字段违规等写入质量表，支持自动巡检

2.3 写入与检查层的位置（服务代码层）
- storage/：数据库写入接口与实现
- checks/：检查与健康报告聚合


==================== 3. 长期规划（长期目标） ====================
3.1 可扩展维度
- 采集方式扩展：REST/WS 之外可新增（如 File/Replay）而不影响现有目录语义
- 工具扩展：新增工具只需要新增对应适配器文件（如 Binance.py/OKX.py），不需要改动骨架
- 行情类型扩展：在不破坏既有数据的前提下逐步纳入更多种类：
  - mark price、funding rate、liquidations、open interest 等
  - 以及更细粒度数据（逐笔、盘口增量/快照等）

3.2 目标状态（理想形态）
- 全链路：采集 -> raw 落库 -> 校验 -> 结构化派生 -> 对外查询/消费
- 数据可回放：任意时刻可从 raw 重建结构化表，保证演进可控
- 字段契约化：对外/对内明确“请求字段”，通过 registry 与 normalize 严格对齐，杜绝字段漂移导致的不可维护

3.3 演进策略（渐进式）
- MVP：单币种 + raw 落库 + 基础健康检查
- Phase 2：多币种 + typed 表（candles/trades）派生
- Phase 3：盘口体系（update + snapshot）与重建工具
- Phase 4：聚合层（连续聚合/指标计算）与稳定 API
